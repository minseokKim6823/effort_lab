# effort 라우터 수정과 재측정

2026-10-09 실측, 2026-10-11 중단 기록 확인. 개발 실험은 완료되어 독립 감사를 통과했다. 수정 정책은 개발 문제 6개를 모두 맞혔지만 기존 정책보다 총토큰을 8.42% 더 사용했다. 정답 수가 늘어난 항목도 두 정책의 effort가 같았으므로, 개발 결과만으로 라우팅 개선을 입증하지 못했다. 새 24문제 평가는 23번째 execution에서 구독 사용 한도로 중단됐으며 마지막 사용량이 미확인이다. 전체 평가의 절감률은 산출하지 않는다.

## 수정한 코드와 가설

기존 `rules-1.1`은 점화식·재귀 수열·최단 경로를 보통 medium으로 시작했다. 이전 v2 기록에서는 재귀 수열의 medium 첫 시도가 두 반복 모두 실패했고, 첫 반복의 실패 호출 3,777토큰이 단순 작업에서 얻은 절감을 넘었다. 실패한 낮은 effort 호출도 전체 입력을 다시 소비한다는 점을 수정의 근거로 삼았다.

`rules-1.2`는 두 부분을 바꿨다.

- 점화식·재귀 수열·최단 경로 신호가 있으면 high로 시작한다. 그 밖의 점수 계산과 단순 작업 선택 규칙은 유지한다.
- 자동 정책에서 low 또는 medium 답변이 검증에 실패하면 high로 한 번만 재시도한다. 기존 low → medium → high 단계에서는 최대 두 번 재시도했다.

라우터는 작업 문자열과 사용자가 지정한 risk만 받는다. 문제 ID·정답·채점 결과를 최초 effort 선택에 사용하지 않는다. API에는 고정 effort 비교를 위한 선택적 `strategy` 입력을 추가했으며, 생략하면 기존처럼 자동 정책을 사용한다. 재시도 여부는 정답을 가진 로컬 검증기가 결정한다.

구현과 사전 계획은 [EffortRouter.java](../backend/src/main/java/dev/effortlab/EffortRouter.java), [EvaluationService.java](../backend/src/main/java/dev/effortlab/EvaluationService.java), [실험 계획](effort-v4-plan.md)에 있다.

## 네 실행 방식과 통제

| 방식 | 최초 effort | 실패 후 동작 |
|---|---|---|
| HIGH | 항상 high | 재시도 없음 |
| LOW | 항상 low | 재시도 없음 |
| LEGACY | 기존 `rules-1.1` 선택 | low → medium → high 순서로 상승 |
| CANDIDATE | 수정 `rules-1.2` 선택 | 낮은 effort 실패 뒤 high 한 번 |

모든 방식은 모델 `gpt-5.6-luna`, Codex CLI `0.153.4`, 답변 전용 지시문, 같은 작업 문자열과 plain answer 형식을 사용한다. 기존 v3의 단건 JSON wrapper 결과와 직접 절감률을 비교하지 않는다. 각 방식의 Java 프로세스는 같은 환경 사본과 작업 디렉터리를 쓰고 API 키 환경변수는 모두 제거했다. 모델에는 작업 문자열만 전달하며 정답은 로컬 검증기에만 전달한다.

문제마다 네 방식의 순서를 한 칸씩 회전한다. 평가의 두 번째 12문제 블록은 한 칸 더 회전하여 같은 가족의 두 인스턴스가 서로 다른 순서로 실행되게 한다. 모델 호출은 순차 실행하고, 각 문제·방식 조합은 한 번만 실행한다. 자동 정책의 실패 호출과 재시도 비용도 모두 포함한다.

기존 jar는 알려진 SHA256에 고정하고 두 핵심 소스를 기준 커밋 `e4f179d`와 대조한다. 수정 jar는 빌드 전후 소스 해시가 일치한 빌드 receipt와 대조한다. Node wrapper뿐 아니라 실제 네이티브 `codex.exe` 해시도 manifest에 보존한다. 소스 사본, API 응답, 원본 CLI JSONL을 보존하고 별도 감사기가 사용량·정답·선택 effort·재시도 순서를 다시 계산한다.

개발 문제는 공개된 v3의 `b01,b04,b02,b05,b08,b09` 여섯 개다. 개발 한 번의 토큰 중단 기준은 140,000이다. 이후 평가는 기존 12가족의 새 인스턴스 두 개씩, 총 24문제이며 seed는 `20261007,20261008`이다. 기존 v2/v3와 prompt 중복이 없고 계산 및 독립 정답 검증을 유지했다. 평가 중단 기준은 500,000토큰이다. 중단 기준은 execution 사이에서 검사하므로 마지막 execution 비용만큼 초과할 수 있다.

## 개발 실험: development-1

[감사 결과](../results/effort-v4/development-1/metrics.json)는 `AUDIT_PASS`다. 6문제 × 4방식의 24개 execution에서 실제 호출도 24회였고 재시도는 발생하지 않았다. 알려진 전체 사용량은 99,037토큰이며 사용량 누락과 실행 중 소스 변경은 없었다. 첫 호출 정답과 최종 정답은 아래 표에서 같다.

| 방식 | 입력 | 출력 | 출력 중 reasoning | 캐시 입력 | 총토큰 | 정답 | 재시도 |
|---|---:|---:|---:|---:|---:|---:|---:|
| HIGH | 22,505 | 1,945 | 1,874 | 1,792 | 24,450 | 4/6 | 0 |
| LOW | 23,510 | 1,541 | 1,472 | 0 | 25,051 | 4/6 | 0 |
| LEGACY | 22,489 | 1,278 | 1,209 | 1,792 | 23,767 | 5/6 | 0 |
| CANDIDATE | 24,135 | 1,634 | 1,565 | 3,584 | 25,769 | 6/6 | 0 |

총토큰은 입력 + 출력이다. reasoning은 출력에 포함되고 캐시 입력도 입력에 포함되므로 두 값을 총토큰에 다시 더하지 않는다. 이 표는 토큰 수 비교이며 캐시별 요금이나 구독 한도 절감액을 계산한 결과가 아니다.

### 비용 변화의 구성

다음 표는 CANDIDATE에서 각 비교 방식의 수치를 뺀 값이다. 양수는 사용량 증가를 뜻한다.

| 비교 기준 | 입력 차이 | 출력 차이 | 총토큰 차이 | 총토큰 증가율 | 최종 정답 차이 |
|---|---:|---:|---:|---:|---:|
| HIGH | +1,630 | −311 | +1,319 | +5.39% | +2 |
| LOW | +625 | +93 | +718 | +2.87% | +2 |
| LEGACY | +1,646 | +356 | +2,002 | +8.42% | +1 |

수정 정책의 기존 정책 대비 추가 비용 2,002토큰은 입력 1,646개와 출력 356개로 나뉜다. 작업 문자열이 같아도 관측 입력량은 같지 않았다. 예를 들어 `b01`은 두 자동 정책 모두 low를 선택하고 똑같은 16토큰 답변을 출력했지만 수정 정책의 입력이 696토큰 더 많았다. 따라서 관측된 총비용 차이 전체를 effort 규칙 변경의 효과로 설명할 수 없다.

실제로 최초 effort가 달라진 개발 문제는 두 개다.

| 문제 | 기존 → 수정 effort | 기존 / 수정 정답 | 입력 차이 | 출력 차이 | 총토큰 차이 |
|---|---|---|---:|---:|---:|
| b05 모듈러 점화식 | medium → high | 정답 / 정답 | 0 | +51 | +51 |
| b08 가중 그래프 경로 | medium → high | 정답 / 정답 | +696 | −66 | +630 |

두 문제 모두 기존 정책의 첫 시도도 정답이었다. 이 개발 실행에서는 실패 재시도를 미리 피하는 이득을 확인하지 못했다. 재시도 자체가 한 번도 없어서, low 실패 뒤 곧바로 high로 이동하는 새 규칙의 실제 비용 효과도 아직 관측하지 못했다.

### 정답 수 차이의 해석

기존 정책과 수정 정책의 유일한 정오 차이는 `b09` 선행 작업 일정 수였다. 기존 정책은 `16`, 수정 정책은 정답 `21`을 출력했다. 그러나 두 정책 모두 처음부터 high였고 재시도도 없었다. 따라서 이 한 문제의 개선을 라우터 수정의 성과라고 해석하지 않는다. 고정 HIGH도 같은 문제에서 `26`을 출력했다. 같은 effort의 별도 호출에서 서로 다른 결과가 나온 기록이다.

고정 HIGH의 나머지 실패는 `b01` 제품 코드 변환의 출력 형식이었다. 모델은 `'SHIPMENT-6PU-22L5-REV-D'`처럼 바깥따옴표를 포함했고 기대 정답은 따옴표가 없는 문자열이었다. 원문은 문자열을 따옴표로 표시하면서 “문자열만 출력”이라고 지시하므로 따옴표 포함 여부의 모호성이 있다. 사전 EXACT 채점에 따라 실패로 유지했으며 결과를 본 뒤 이 문제를 제외하거나 따옴표 제거 규칙을 추가하지 않았다. 이 결과는 의미상 대문자 변환 자체의 실패와 구별해서 읽어야 한다.

## 개발 후 고정한 선택

[freeze.json](../results/effort-v4/freeze.json)에 2026-10-09T10:51:53.646Z의 결정을 기록했다. 두 번째 개발 반복 없이 `rules-1.2`를 유지하고 예정된 새 문제 평가를 한 번 진행한다. 고정한 커밋은 `c42f49f16a83b7f6fc7c9dd8b3e3d8b263f8dcb8`이며 jar·소스·개발 감사 결과 해시도 함께 저장했다.

개발 결과에서 새로 바꾼 경로의 실패는 없었고, 정답 수 차이는 변경되지 않은 high 호출에서 발생했다. 이를 근거로 규칙을 다시 조정하면 한 번의 생성 변동에 맞출 위험이 있어 추가 조정을 하지 않았다. 개발에서 비용 절감을 달성했다고 주장하지 않으며, 이전의 점화식 재시도 가설을 고정된 새 인스턴스에서 확인한다.

## 새 24문제 평가: holdout-1 — 중단·미완료

2026-10-11에 중단 기록을 확인했다. `holdout-1`은 2026-10-09에 예정된 96개 execution 중 22개를 완료한 뒤, 23번째인 `requests/022.json`의 `h06 / CANDIDATE` 실행에서 사용 한도 오류로 중단됐다. 원본 CLI JSONL에 사용 한도 도달 오류와 `turn.failed`가 남아 있다. 저장된 요청 기록은 오류 응답을 포함해 23개이며, 전체 24문제를 네 방식으로 비교한 완료 결과가 아니다.

확인된 사용량은 **95,721토큰**이다. 완료된 22개 execution에는 재시도를 포함해 사용량이 알려진 모델 호출 24회가 있다. 해당 원본 JSONL의 사용량·출력과 저장 응답, 요청·trace 해시 및 알려진 토큰 합계가 일치하는 것을 확인했다. 마지막 호출의 사용량을 수신하지 못해 `run.json`은 `status: ERROR`, `unknownUsage: true`로 끝났다. 마지막 API 응답의 `totalTokens: 0`은 확정된 무료 호출을 뜻하지 않는다. 전체 실행의 최종 사용량은 알 수 없으며, 알려진 비용을 완결된 실험 비용으로 취급하지 않는다. 실행 중 소스 변경은 없었다.

기존 감사기를 다시 실행한 결과는 [AUDIT_FAIL](../results/effort-v4/holdout-1/metrics.json)이다. 완료 상태를 충족하지 못해 품질·절감 비교를 승인하지 않았다. 중간 결과에서 일부 문제나 방식만 골라 24문제 정답률 또는 토큰 절감률을 발표하지 않는다. [run.json](../results/effort-v4/holdout-1/run.json), [오류 요청](../results/effort-v4/holdout-1/requests/022.json), 원본 CLI JSONL을 포함한 [전체 기록](../results/effort-v4/holdout-1/)은 그대로 보존한다.

추가 검증을 실행할 경우 같은 고정 정책·데이터의 전체 평가를 별도 `holdout-2`에 새로 기록한다. `holdout-1`의 중간 결과에 새 호출을 이어 붙이거나 기존 기록을 덮어쓰지 않는다. 새 실행도 완료·독립 감사를 통과한 뒤에만 네 방식의 첫 호출/최종 정답과 비용을 비교할 수 있다.

## 해석의 한계

- 자동 정책의 재시도는 정답을 아는 EXACT 검증기가 실패를 판별할 수 있다는 전제다. 동등한 검증 수단이 없는 일반 업무에서 같은 행동과 품질을 보장하지 않는다.
- 평가 문제는 익숙한 합성 12가족의 새 인스턴스다. 새로운 업무 유형으로의 일반화 평가가 아니며, 한 번씩 실행한 결과로 통계적 유의성이나 안정적인 우위를 주장하지 않는다.
- 제품 코드 변환군은 입력의 바깥따옴표를 출력에도 유지할지 모호하다. 모든 방식을 동일한 고정 채점으로 비교하지만 형식 실패가 정답 수와 재시도 비용에 영향을 줄 수 있다.
- 같은 작업·effort라도 입력 토큰, 캐시, 출력, 정답 여부가 달라질 수 있다. 순서 회전과 공통 환경은 비교를 개선하지만 공급자 측 동적 입력과 생성 변동까지 제거하지 못한다.
- 두 정책이 같은 effort를 선택한 문제의 정오 차이는 그 자체로 라우팅 개선의 증거가 아니다. 경로가 달라진 문제와 실패 재시도 비용을 함께 봐야 한다.
- CLI JSONL은 출력과 사용량을 뒷받침한다. 실행 effort는 저장된 정책·API 시도 기록·소스로 검산하며, JSONL 자체가 요청의 전체 지시문과 실행 설정을 독립적으로 증명하지는 않는다.
