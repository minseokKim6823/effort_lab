# 라우터 수정·개발 실험·새 문제 평가 계획

2026-10-06 초안, 2026-10-09 실측 전 확정. 목표는 개별 작업의 effort를 선택하는 코드를 바꾸고, 재시도까지 포함한 총토큰과 정답 수가 기존 정책 및 고정 effort보다 나아지는지 확인하는 것이다.

## 코드 후보와 비교군

기존 `rules-1.1`의 재귀 수열은 v2 두 반복에서 medium 첫 시도가 실패했다. 첫 반복의 실패 호출 3,777토큰이 단순 작업에서 얻은 절감을 넘었다. 첫 후보 `rules-1.2`는 점화식·재귀 수열·최단 경로를 high로 시작하고, low 또는 medium 실패 뒤에는 high로 한 번만 재시도한다. 문제 ID·정답·평가 결과를 라우터 입력으로 사용하지 않는다.

네 팔은 고정 HIGH, 고정 LOW, 기존 정책 LEGACY, 수정 정책 CANDIDATE다. 고정 팔은 한 번만 호출하고 자동 팔은 정책이 정한 재시도를 수행한다. 모든 팔은 같은 모델 `gpt-5.6-luna`, CLI `0.153.4`, 답변 전용 지시문, plain answer 형식을 쓴다. 묶음 처리·문맥 축소 성과를 섞지 않는다.

## 개발과 평가 분리

개발 문제는 공개된 v3의 `b01,b04,b02,b05,b08,b09` 여섯 개로 고정한다. 변환·추출·집계·반복 계산·경로·경우의 수를 포함하며 모든 문제를 네 방식으로 실행한다. 개발 결과에 따라 두 번째 후보를 만들 수 있으나 첫 실행과 실패 기록도 보존한다. 개발 실측은 최대 두 번으로 제한한다.

개발을 마친 뒤 소스와 정책을 고정하고 `results/effort-v4/cases.json`의 24문제를 한 번씩 네 팔로 평가한다. seed 20261007/20261008, 기존 12가족의 새 인스턴스 두 개씩이며 기존 v2/v3 prompt와 중복되지 않는다. 문제 유형·크기·독립 정답 계산은 기존 생성기와 같다. 기존 PRNG 하위 비트 주기로 동일 문제가 생기는 것을 막기 위해 새 생성기만 32비트 전체 상태를 범위에 매핑한다. 모델 결과를 보고 문제를 제외하거나 바꾸지 않는다. 이 세트는 유형 밖 일반화 평가가 아니다.

평가 결과를 보고 코드를 바꾸면 그 결과는 새 정책의 최종 평가로 사용하지 않는다. 추가 검증은 별도 데이터와 계획이 필요하다.

## 실행 통제와 비용

이전 코드의 jar와 수정 코드의 jar를 같은 Java·Node 환경과 같은 작업 디렉터리에서 실행한다. API 키 환경변수를 두 프로세스에서 모두 제거하고 기존 Codex 구독 로그인을 사용한다. API `/execute`에 정답은 로컬 검증용으로만 보내며, ModelGateway는 작업 문자열만 모델에 보낸다. HIGH/LOW 기준선을 재현하도록 선택적 strategy 입력을 추가하고 기존 생략 동작은 자동으로 유지한다.

문제마다 `HIGH,LOW,LEGACY,CANDIDATE` 순서를 하나씩 회전하고, 평가의 두 번째 12문제 블록은 추가로 한 칸 회전한다. 동시에 모델을 호출하지 않는다. 개발은 24개 execution, 평가는 96개 execution이며 실제 호출 수에는 실패 재시도도 포함한다. 개발 한 번의 총토큰 중단 기준은 140,000, 평가 기준은 500,000이다. 기준은 execution 사이에 검사하므로 마지막 execution의 호출들만큼 넘을 수 있다. 각 모델 호출은 180초 제한이다. 사용량 누락·호출 오류 시 기록 후 중단하고, 같은 결과 디렉터리의 자동 재개·덮어쓰기는 금지한다.

manifest에 문제·순서·정책·jar/CLI 및 소스 해시와 실제 소스 사본을 보존한다. CLI JSONL과 각 API 응답을 별도 파일로 남긴다. 서버는 실행기가 시작한 프로세스 트리만 정리한다. 현재 저장된 구독 자격 증명은 manifest나 결과에 저장하지 않는다.

## 판정

독립 감사로 응답·ID·usage·정답·재시도 순서를 검산한다. 입력·출력·추론·캐시 입력·전체 토큰·첫 호출 정답·최종 정답·재시도 수와 항목별 결과를 모두 공개한다. reasoning은 output 안에 포함한다.

수정 정책이 기존 정책보다 좋아졌는지와 고정 high/low보다 좋아졌는지를 각각 보고한다. high보다 토큰이 줄어도 정답 수가 떨어지면 품질 유지 성과로 발표하지 않는다. 고정 low가 더 낫다면 자동 정책의 이점을 주장하지 않는다. 입력 토큰이 서비스·문맥의 동적 변화로 달라질 수 있으므로 total과 output 결과를 함께 해석한다. 한 번의 합성 문제 평가로 통계적 유의성이나 일반 업무의 품질 보장을 주장하지 않는다.

```powershell
node scripts/generate-effort-cases.mjs --check
./scripts/build-effort-v4.ps1
node scripts/measure-effort-v4.mjs development-1 --validate-only
node scripts/measure-effort-v4.mjs development-1
node scripts/audit-effort-v4.mjs development-1
# 개발 후 정책을 고정한 다음에만 실행
node scripts/measure-effort-v4.mjs holdout-1
node scripts/audit-effort-v4.mjs holdout-1
```
